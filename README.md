# csv-tidy

CSV / Excel の汚れを見つけて、直して、書き出すツール。

**ファイルはサーバーへ送信しません。** すべてブラウザの中だけで処理します。
ブラウザにも保存しません（localStorage / IndexedDB / Cookie を使いません）。タブを閉じれば消えます。

> 元のファイルは変更しません。書き出した結果は必ずご確認ください。

**→ [触ってみる](https://hiros0921.github.io/csv-tidy/)**

React 19 + TypeScript（`strict`）/ Vite / Web Worker。サーバーはありません。

## 「送信されません」を、測って示す

主張を言葉で書くだけでは弱いので、開発者ツールで数えました。
**読み込み → 検出 → 修正 → 再検査 → 書き出し**まで通した結果です。

| | 件数 |
|---|---|
| ページの読み込み | 3件（HTML・JS・CSS） |
| 操作中に増えた要求 | **1件**（Worker のスクリプト。同じ配信元） |
| **外部（別オリジン）への要求** | **0件** |
| favicon の要求 | **0件** |
| Cookie / localStorage / sessionStorage / IndexedDB | すべて空 |

公開先（GitHub Pages）でも同じです。読み込みから書き出しまで通して、
要求は **HTML・JS・CSS・Worker の4件だけ**、いずれも同じ配信元でした。

見落としやすい経路を、先に潰してあります。

- **Webフォントを使わない。** Google Fonts を1本読むだけで、この主張は崩れます。システムフォントだけにしました
- **favicon を埋め込む。** 指定しないとブラウザが `/favicon.ico` を取りに行き、通信が1件出ます。`data:` で埋めれば取りに行く先がありません
- **外部CDNを使わない。** SheetJS も含め、すべてビルド時に同梱します
- **ソースマップを出さない。** 外部参照が残りません

なお、生成物の中に `http://schemas.microsoft.com/...` という文字列が入っています。
これは SheetJS が持つ **XML の名前空間**で、取りに行く先ではありません。
（Network タブに出ないことが、そのまま証拠になります）

## READMEに書きにくいこと：外した見積もりが3件あります

先に書きます。**このプロジェクトで一番学んだのは、測る前に決めないことでした。**

### ① 「平坦なバッファに詰め替えれば速い」→ 14倍遅かった

100万セルを Worker とやり取りするコストを心配して、
「文字列の配列ではなく、1本のバイト列＋オフセット配列に詰め替えて転送する」案を立てていました。
転送がゼロコピーになるからです。測りました。

| | |
|---|---|
| 配列をそのまま `postMessage`（送る側の停止） | **45 ms** |
| 平坦バッファへの**詰め替え** | **621 ms** |
| 詰め替えたものを転送（停止） | 1.7 ms |

**避けようとしたコストの14倍を、避けるために払うところでした。** 案は捨てました。

### ② 「列の一括置換は Worker へ回さないと固まる」→ 20倍の見積もり違い

10万行の列1本を走査して置換するコストを心配していました。実測は **2.3ms** です。

原因は単純で、**200万セル（表全体）と10万セル（1列）を混同していました。**
桁を1つ間違えた見積もりで、設計を1つ複雑にしかけていました。

### ③ `¥8,500` が `?8,500` になった。アプリの不具合を疑ったが、違った

書き出したデータで通貨記号が壊れていて、最初は自分のコードを疑いました。原因はこれです。

| 文字 | Shift-JIS（CP932） |
|---|---|
| **半角の `¥`（U+00A5）** | **無い。`?` になる** |
| 全角の `￥`（U+FFE5） | ある |
| `\`（バックスラッシュ） | ある |

壊れていたのは検証データを作った時点で、アプリは正しく読んでいました。
**日本語のCSVを扱うなら、ここは一度は踏む場所**だと思います。テストに固定してあります。

この3件は、どれも**測ったから分かった**ことです。①と②は測らなければ、
「そういうものだ」と信じたまま複雑な実装が残っていました。

## 設計の中心：型で不正な状態を作れなくする

「TypeScript で書きました」は実績になりません。**型で何を防いだか**を書きます。
防いでいるものは2つです。

### 1. 「まだ調べていない」と「調べて問題なし」を混同させない

```typescript
type CellState =
  | { kind: 'unchecked' }                                   // まだ調べていない
  | { kind: 'clean' }                                       // 調べて、問題なし
  | { kind: 'issue'; issues: NonEmpty<Issue> }              // 問題あり
  | { kind: 'fixed'; original: string; by: FixSource;
      resolved: NonEmpty<Issue>; remaining: readonly Issue[] }
```

両方を「問題なし」で表すと、**解析が途中で止まったセルが、きれいなセルと同じ扱いで書き出されます。**

`issues` は `NonEmpty<T> = readonly [T, ...T[]]` にしてあります。
`{ kind: 'issue', issues: [] }`（問題ありだが0件）は、`clean` と区別できない中途半端な状態です。作れなくしました。

範囲外の添字や、詳細を失ったセルは **`clean` ではなく `unchecked` に倒します。**
握りつぶして「問題なし」にすると、そのまま書き出されるからです。

### 2. 表記揺れの統一先を、機械が決められないようにする

仕様の禁止事項に「表記揺れの統一先を、機械が勝手に決めない」があります。
これを規約ではなく**型**にしました。

```typescript
type Remedy =
  | { kind: 'auto'; to: string }                     // 迷う余地がない
  | { kind: 'choice'; options: NonEmpty<Candidate> } // 人が決める
  | { kind: 'none' }                                 // 機械には判断できない

// 自動修正は auto しか受け取らない
function applyAuto(original: string, remedy: Extract<Remedy, { kind: 'auto' }>): string
```

表記揺れ・和暦・前ゼロの `Remedy` は必ず `choice` なので、
**それらを自動で当てるコードはコンパイルが通りません。**

候補には**出現件数を添えます**が、**多数派に印は付けません。**
件数は事実、推奨は判断です。線はそこに引きました。

### 型で防いでいることを、テストで固定する

```typescript
const choice: Remedy = { kind: 'choice', options: [...] }
// @ts-expect-error 表記揺れの統一先を機械が決めることは、型が許さない
applyAuto('(株)甲野商事', choice)
```

`@ts-expect-error` は「**コンパイルが通らないこと**」を検査します。
型が緩められて通るようになると、この行のほうがエラーになります。
**「型で防いでいます」は、防げなくなったときに壊れる形にしておかないと主張になりません。**

### 型と格納を分ける

判別可能な合併型は表現力がありますが、**10万行 × 20列 = 200万セル**のオブジェクトは作れません。
そこで、**型は境界で作り、格納は列指向のフラット配列**にしました。

```
格納  状態コード      Uint8Array 1本（200万セルで 2MB）
      三分岐の区分    Uint8Array 1本
      説明文          問題があったセルだけ Map に。clean なセルは何も持たない
型    CellView        塗るための型。2バイトから作る
      CellState       説明するための型。詳細が手元にあるときに作る
```

`Uint8Array` は Transferable なので、**Worker からの戻りもゼロコピー**になります。
「メモリが持たない」と「Worker の戻りが重い」が、同じ形で解けました。

型を1つにまとめて「説明文の無い issue」を許すと、
「まだ調べていない」と「調べたが説明文がここに無い」が混ざります。
それは最初に潰したはずの混同なので、**型を2つに分けました。**

## 誤検出を抑える作り

仕様に「誤検出が続くと、人は画面を流し読みするようになる」とあります。
**本物の問題が見逃されるので、網は狭くしてあります。**

**セルを見る前に、列全体を見ます。** 8割が一致すれば、その列を「電話番号の列」と決めます。
電話番号の列だと決まって初めて「電話番号の形が揃っていない」と言えます。

- **郵便番号を電話番号より先に見ます。** 7桁の数字は電話番号としても読めるので、順番を誤ると取り違えます
- **表記揺れは、列内に表記が2種類以上あるときだけ**出します。1種類なら揺れていません
- **法人格を含む値だけ**を表記揺れの対象にします。一般の語まで見ると、別語を同一視します
- **異常値は「桁数が列の中央値より3桁以上多い」だけ**に限定しました

7列のサンプルで、見立ては全問正解でした（文字列・文字列・電話番号・郵便番号・数値・日付・数値）。

### 直さないと決めたもの

| | 理由 |
|---|---|
| 和暦（令和8年1月25日） | 西暦へ一意に直せますが、**元が和暦だった事実が失われます**。公文書の転記では和暦のままである必要があります |
| 前ゼロ（`007`） | 数値に直すと `7` になります。商品コードが壊れます |
| 重複行 | どちらを残すかは、その会社の事情です。片方が最新の更新かもしれません |
| 空欄 | 埋めてよいかは機械には分かりません |

## 性能の実測値

すべて本番ビルド・Chrome・10万行 × 10列（100万セル）です。

### 表示（仮想スクロール）

**行数を10倍にしても、DOM に載る行数は変わりません。**

| 総行数 | 先頭での DOM 行数 | 中央での DOM 行数 | スクロール量 |
|---|---|---|---|
| 1万行 | 29 | 35 | 26万 px |
| 5万行 | 29 | 35 | 130万 px |
| **10万行** | **29** | **35** | **260万 px** |

スクロール中のフレーム間隔（180フレーム）。

| | 中央値 | p95 | 最長 |
|---|---|---|---|
| 縦 | 16.7 ms | 17.6 ms | 22.2 ms |
| 縦横同時 | 16.7 ms | 17.7 ms | 29.3 ms |

中央値 16.7ms は 60fps です。

### 読み込みと検出（Web Worker）

| | |
|---|---|
| 表が出るまで | **250〜266 ms** |
| 100万セルの検出が終わるまで | 約 1.8〜2.2 秒 |
| **検出中のフレーム間隔** | 中央値 **16.7 ms** / p95 17.4 ms |
| 50ms を超えたフレーム | **0本** |

検出が走っている2秒間も、スクロールできますし表も操作できます。

### 修正・再検査・書き出し

| 操作 | 時間 | 50ms超のタスク |
|---|---|---|
| 列ごと統一（33,333件） | 17 ms | なし |
| 取り消し | 13 ms | なし |
| 再検査（100万セル） | 押した瞬間 60 ms・完了まで 1,741 ms | 60ms が1本 |
| 書き出し UTF-8（BOM付き） | 押した瞬間 45 ms・完了まで 249 ms（10.3MB） | なし |
| 書き出し Shift-JIS | 押した瞬間 46 ms・完了まで 453 ms（8.7MB） | なし |

「押した瞬間」は、値の配列を Worker へ渡すためにメインスレッドが止まる時間です。
**人がボタンを押したときにしか起きません。**

### 配信サイズ（gzip）

| | |
|---|---|
| 最初に読むもの | **155 kB** |

SheetJS を動的 import にしたのは、**CSV しか使わない人に読ませる理由がない**からです。

ブラウザのタブが使えるメモリには上限があります。**このツールは10万行を目安**にしています。
30MB を超えるファイルは、**読み込む前に確認**を出します。黙って落ちるより先に伝えるためです。

## 文字コード（日本のCSVで最重要）

Excel が吐く CSV は Shift-JIS（CP932）です。UTF-8 の BOM 付き / なしも混ざります。

**判定に確信度を付けました。** 「判定した」と「たぶんこれだろう」は違います。

| 確信度 | 根拠 |
|---|---|
| `certain` | BOM がある。バイト列に書いてあるので外れようがない |
| `high` | UTF-8 として妥当な多バイト列を含む／ASCIIのみ／UTF-8として不正でSJISと一致 |
| `low` | 統計判定だけ |
| `fallback` | 決め手なし。Excel の CSV で最も多い CP932 を既定にする |

UTF-8 の妥当性検査は自前です。**冗長符号化とサロゲート値も弾きます**。
規格に照らした可否なので、統計より強い根拠になります。

判定は外れる前提で、**結果と確信度を画面に常時表示し、人が変更できます。**
変更すると、**元の File からバイト列を読み直します**（復号済みの文字列からは戻せません）。

### なぜ BOM 付きが要るのか

**BOM なしの UTF-8 を Excel で開くと、環境によっては CP932 と解釈されて文字化けします。**
日本の実務ではここで必ず1回はつまずきます。書き出しの既定を「UTF-8（BOM付き）」にしました。

### なぜ書き出しは CSV だけか

xlsx で書き出すと、**文字コードを選ぶという話が消えます**（中身は UTF-8 の XML）。
このツールの主張の1つが「Excel が読める形で、文字コードを選んで出す」ことなので、
そこを xlsx に逃がすと薄まります。**読むのは CSV と xlsx、書くのは CSV だけ**にしました。

### 書けない文字を、書く前に数える

`encoding-japanese` は表せない文字を**黙って `?` に置き換えます**。
それは「直したつもりが壊れていた」の典型なので、書き出す前に出します。

```
Shift-JIS（CP932）では書けない文字が2種類ありました。
書き出したファイルでは ? になっています。
  [— 1件] [🙂 1件]
残したい場合は、文字コードを UTF-8（BOM付き）にして書き出し直してください。
```

`㈱` `髙` `﨑` `①` `ヱ` `ヴ` は CP932 にあるので、**書けないとは言いません。**
ここを誤検出すると、直す必要のないものを直させることになります。

## 変更履歴と、取り消し

**この2つは別のものとして扱っています。**

| | 取り消し（undo） | 変更履歴 |
|---|---|---|
| 目的 | 作業のやり直し | 監査 |
| 上限 | **直近50操作** | なし |
| 捨てるか | 古いものから捨てる（**捨てたことは画面に出す**） | **捨てない** |
| 取り消しの扱い | スタックから消える | **1行として残す** |

取り消しも記録します。**「勝手に直された」だけでなく「直したはずが戻っている」にも答える**ためです。

書き出す履歴は、1変更＝1行です。

```
通番,日時,操作,決めたのは,範囲,行,列,前,後,種別
1,2026-08-20T13:42:31.079Z,修正,人,列,2,取引先名,(株)甲野商事,株式会社甲野商事,notation_variant
2,2026-08-20T13:42:31.734Z,修正,機械,セル,2,担当者,"佐藤 花子 ",佐藤 花子,trailing_space
```

### 「決めたのは」と「範囲」を、別の軸にした

仕様は「自動で直したものと、人が直したものを区別すること」を求めています。
実装してみて、**1つの軸では表せない**と分かりました。

```typescript
type FixSource = {
  decidedBy: 'machine' | 'human'   // その値を決めたのは誰か
  scope: 'cell' | 'column'          // どの範囲に当てたか
  column: number | null
}
```

「**列全体を機械が直した**」（前後の空白をまとめて取る）も、
「**1セルを人が直した**」もあります。監査で問われるのは `decidedBy` のほうです。

### 取り消しは、値だけでなく状態も戻す

変更1件は、前の値だけでなく**前の状態**も持ちます。
これが無いと、**取り消したときにセルが「問題なし」になります。**
問題を直して、それを取り消したなら、問題ありに戻るのが正しい。

### 空白を、見える形にする

このツールがいちばん多く直すのは前後の空白です。
ところが履歴に「`佐藤 花子 ` → `佐藤 花子`」と並んでいて、**何が変わったか読めませんでした。**

**記録があっても読めなければ、記録していないのと同じです。**

表示のときだけ `␣`（半角）`□`（全角）`⏎`（改行）に置き換えました。
**値そのものは変えていません。** ここを曖昧にすると、書き出しで事故ります。

## 再検査

修正したあと、**「再検査」を押すと、いまの値でもう一度調べ直します。**

- **人が押したときだけ**走ります。修正のたびに全件走査すると固まります
- **Worker で、進捗表示つき**です
- **直したセルも例外にしません。** 直したつもりで問題が残っていれば、また問題として出ます

たとえば、末尾の半角空白を「直したつもりで全角スペースにした」とき、再検査後はこう出ます。

```
2 行目・担当者   佐藤 花子□
[直しました（人が決定・セル単位）]  元の値：佐藤 花子␣
[自動で直せる]  末尾に空白があります
```

**変更履歴は消えません。** 再判定で問題なしになっても、「直した」記録は残ります。

集計が減っていくのが、作業が進んでいる目印になります（10万行で 110,000 → 10,000）。

### SheetJS を npm から入れていない理由

`npm install xlsx` で入るのは **0.18.5** で、既知の脆弱性2件に「**修正なし**」と出ます。
SheetJS が 0.19 以降を npm ではなく自社配布へ移したためです。
公式配布の 0.20.3 を `package.json` に直接指定して、`npm audit` を 0件にしました。
**ビルド時に同梱するので、実行時の外部通信は増えません。**

## 構成

```
src/
  domain/     React も DOM も Worker も知らない層。純粋関数だけ
    cell.ts     CellState / CellView と、状態コード
    issue.ts    Issue と Remedy（三分岐）
    edit.ts     修正・取り消し・変更履歴
    detect/     検出（列を見る → セルを見る → 行の重複を見る）
  io/
    encoding.ts 文字コードの判定と復号
    parse.ts    CSV / xlsx → 行の配列
    write.ts    CSV の組み立てと符号化
  worker/     読み込み・検出・再検査・書き出し。すべてここで走る
  ui/         React。表示と操作だけ
```

`domain/` を分けたので、**ブラウザも Worker も起動せずに `vitest` で検査できます。**
112件のテストは、DOM を立てずに 0.2 秒で通ります。

### 状態管理にライブラリを足していません

React 標準（`useState` / `useReducer`）で足りています。条件は1つで、
**10万行の値を state に入れないこと**です。値の配列は書き換えても参照が変わらないので、
更新の合図は別に持っています。10万行の配列を作り直す必要はありません。
